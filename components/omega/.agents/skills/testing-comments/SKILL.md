# Testing comments

A reviewer reads the top of the comment to learn what ran and whether it
passed. Someone tracking down a failure later needs every path, commit
and log. Keep the first short and visible, and put the second in a fold.
Do not drop either.

`doc/devGuide/Testing.md` ("What to Include in Your PR Testing Comment")
lists the facts to record. Lay them out like this:

1. A `## Testing` heading. A heading can name the machine when each
   machine has its own comment.
2. One sentence saying what was tested (the branch, or a merge into
   `develop`, with commits) and against which baseline.
3. A table with a row per machine and compiler, and a column each for
   CTests, `omega_pr` and coupled tests: counts, or bit-for-bit with the
   baseline. Leave out rows you never meant to run. A planned row that
   could not run stays in, saying why.
4. A line for each failure or difference from the baseline, naming the
   task or test. Say what caused it only if you checked, and otherwise
   say the cause is not known. Failures unrelated to the branch go under
   their own heading.
5. A `<details>` fold for each row, holding everything else: baseline and
   pull request build paths (`-p`) and work directories, commits, logs,
   the coupled case directories and `TestStatus` lines, norms. Paste
   output there, not above it.
6. If testing was done outside existing or new polaris and ctests,
   provide the commit or branch that was tested and provide the paths to
   the output as above. In addition, indicate what role this test serves
   and why it is not suitable for a ctest or polaris test in 1-2
   sentences.

Comments that the `omega-pr-testing` utility writes already have this
shape. Post them as written, with your findings in its notes file, which
is where the lines in item 4 go.

- Do not restate in prose what the table or a fold already shows.
- Never tick the pull request's checklist boxes. That is the developer's
  job.

## Calibration

Measured over Testing comments on Omega and Polaris pull requests from
2023 and 2024, before any agent wrote there. Leaving out pasted output,
they run 28 words at the median, 57 at the ninetieth percentile, and 129
at the longest. They recorded less than the template now asks for, so
the table and folds will make a comment longer than that. The figures
apply to the prose you write outside them. A recent agent-written comment
ran 606 words, all of it visible.

## Enough

Short, from before the template asked for more:

> ## Testing
>
> CTests all pass on Chicoma-CPU with gnu with a test-merge equivalent to
> this PR. They fail to build because of a cmake module error without
> this update.

Generated by the `omega-pr-testing` utility, with the fold closed:

> ## Testing on chrysalis
>
> Tested the merge of E3SM-Project/Omega#688 (`4185fb3b16`) into
> `develop` (`a67f43530c`) as `e9d2f95a84`, against Polaris' Omega
> submodule (`a67f43530c`).
>
> | Row | CTests | `omega_pr` | Coupled | New build warnings |
> |---|---|---|---|---|
> | chrysalis, intel, openmpi | 62 of 62 passed | 36 of 36 passed | 2 of 2 passed | 0 |
>
> ▶ chrysalis, intel, openmpi

## Too much

A real agent-written comment put the table in, then said the same thing
again in prose:

> Every task now runs to completion. The five diffs are all of the form
> `File ... does not exist`: `main` crashed before writing those outputs,
> so there is nothing to compare against. Every comparison that had a
> file on both sides passed. A clean like-for-like comparison for those
> five tasks needs a fresh baseline once this lands.
