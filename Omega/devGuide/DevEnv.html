Development Environment

As a developer, if you want to lint the code, build the documentation locally or run the omega_buildnml unit tests, you will need your own environment with the necessary packages.

We recommend pixi, which creates the environment from components/omega/pixi.toml. Omega’s CI also uses this environment. If you cannot use pixi, Fallback: conda environment describes how to create a conda environment from components/omega/dev-conda.txt instead.

Installing pixi

If you have not already done so, install pixi:

curl -fsSL https://pixi.sh/install.sh | sh

This installs pixi in ${HOME}/.pixi/bin and adds that directory to your PATH in your .bashrc. Start a new shell (or source ~/.bashrc) before using it. Pixi is a single small executable, so it can stay in your home directory even where your home quota is small.

Keeping pixi off your home quota

Before you create any pixi environments on an HPC machine, decide where pixi will keep its packages.

Pixi downloads each package once into a package cache, and then hardlinks the files from the cache into each environment. Hardlinks only work when the cache and the environment are on the same file system. Otherwise, pixi copies the packages into every environment. The Omega environment is about 2 GB, and every branch or worktree gets its own environment, so copies add up quickly. Home directories on HPC machines usually have small quotas.

To avoid this, add a line like the following to your .bashrc on each machine, pointing at a directory with plenty of space:

export PIXI_CACHE_DIR=/path/with/space/pixi/cache

Set PIXI_CACHE_DIR explicitly even if the default location would have room. On some network file systems, pixi otherwise caches packages inside each workspace, so every branch or worktree gets its own copy of every package.

Pixi puts an environment in components/omega/.pixi of the branch you create it from. If your Omega branches are not on the same file system as PIXI_CACHE_DIR (for example, if your branches are in your home directory but the cache is on a project file system), also tell pixi to put its environments next to the cache:

pixi config set --global detached-environments /path/with/space/pixi/envs

You only need to run this once on each machine. It is saved in ${HOME}/.pixi/config.toml.

For example, on Perlmutter, the home directory is too small for Omega branches, so we recommend cloning Omega somewhere under /global/cfs/cdirs/e3sm/${USER}. Then put the cache on the same file system:

# in ~/.bashrc
export PIXI_CACHE_DIR=/global/cfs/cdirs/e3sm/${USER}/pixi/cache

If you do keep Omega branches in your home directory, this cache alone would make pixi copy packages into each environment in your home directory. In that case, also put the environments on CFS:

# once
pixi config set --global detached-environments /global/cfs/cdirs/e3sm/${USER}/pixi/envs

detached-environments is a global setting. It applies to every pixi workspace you use on that machine, not just Omega. This includes the pixi environments that Polaris creates. All of them will go in this directory instead of next to their workspaces. Environments outside their workspaces are also not deleted when you delete a branch or worktree, so see Removing the environment for how to clean them up.

Avoid scratch file systems that are purged. If files in an environment are purged, the environment stops working and you will need to recreate it.

On a laptop or workstation, the default locations are usually fine.

Creating the environment

From the root of an Omega branch, run:

cd components/omega/
pixi install

Pixi solves for the packages in pixi.toml and installs them. It also writes a pixi.lock file recording exactly what it installed. Omega does not commit this file to the repository (it is in .gitignore), so each branch gets the latest compatible packages when its environment is created.

Activating the environment

To activate the environment, run:

cd components/omega/
pixi shell

This starts a new shell with the environment activated. You can then move around the repository (or anywhere else) and use the tools in the environment. Type exit to leave the shell. You can also run pixi shell from the root of the branch with:

pixi shell --manifest-path components/omega/pixi.toml

If you have not run pixi install yet, pixi shell will create the environment first.

The first time you set up the environment, you need to initiate pre-commit:

pre-commit install

This needs to be done once per environment, so re-run it as necessary if you re-create the development environment.

Please activate this environment each time you commit code. This will ensure that pre-commit and the associated linting utilities are available and that they check your code as it is committed (rather than requiring fix-up commits later on).

Updating the environment

If pixi.toml changes (for example, after you merge or rebase onto a newer develop), pixi updates the environment the next time you run pixi shell or pixi install.

To update the packages to their latest compatible versions without any change to pixi.toml, run:

cd components/omega/
pixi update

Changing the packages

If you add, remove or change the version constraint of a package in pixi.toml, make the same change in dev-conda.txt. CI runs components/omega/ci/check_dev_envs.py to make sure the two files list the same packages and version constraints. You can run it yourself before you commit:

cd components/omega/
ci/check_dev_envs.py

Removing the environment

If you use the default location, the environment is in components/omega/.pixi, so it is deleted along with the branch or worktree.

If you set detached-environments, the environment is outside the branch and outlives it. Before you delete a branch or worktree, remove its environment with pixi clean, which needs the branch’s pixi.toml:

pixi clean --manifest-path <worktree>/components/omega/pixi.toml
git worktree remove <worktree>

pixi clean removes the environments but leaves a small directory behind (a few KB).

If you have already deleted a branch or worktree without running pixi clean, pixi has no command to find its environment. Each environment records the pixi.toml it was created from, so you can list the environments whose pixi.toml no longer exists:

envs_dir=/global/cfs/cdirs/e3sm/${USER}/pixi/envs
for meta in "${envs_dir}"/*/envs/*/conda-meta/pixi; do
  manifest=$(sed -n 's/.*"manifest_path": *"\([^"]*\)".*/\1/p' "${meta}")
  if [ ! -f "${manifest}" ]; then
    echo "${meta%/envs/*/conda-meta/pixi}"
  fi
done | sort -u

Set envs_dir to your detached-environments directory. This lists environments from other pixi workspaces, such as Polaris, as well as Omega. Check the list, then delete those directories with rm -rf. It is worth doing this from time to time so that unused environments do not pile up.

Because environments are hardlinked from the package cache, deleting them frees less space than their size suggests. To free the rest, also clear out the cache with pixi clean cache. Existing environments keep working, and pixi downloads packages again the next time it needs them.

Fallback: conda environment

If you cannot use pixi, you can create a conda environment with the same packages instead. Unlike the pixi environment, this environment is not built in CI, though CI does check that dev-conda.txt lists the same packages as pixi.toml.

Installing Miniforge3

If you have not already done so, you will install Miniforge3:

curl -L -O "https://github.com/conda-forge/miniforge/releases/latest/download/Miniforge3-$(uname)-$(uname -m).sh"
bash Miniforge3-$(uname)-$(uname -m).sh

If you have the space to do so, we recommend installing Miniforge3 somewhere in our home directory. Typically, this file system will be faster than on a scratch space spaces. Also, a conda environment will be rendered useless if its contents get purged. However, conda environments each require several GB of space, which may quickly use up your disk quota so you will need to weigh these trade-offs for yourself.

In what follows, we assume you have Miniforge3 installed in ${HOME}/miniforge3.

You may wish to skip the step in the Miniforge3 installation where it wants to modify your .bashrc. If you allow it to, it will add activation of the conda command and the base conda environment, and this may not be something you want.

If you opt not to allow Miniforge3 to update your .bashrc, it may be helpful to add an alias like the following to your .bashrc:

alias conda_base='
source ${HOME}/miniforge3/etc/profile.d/conda.sh
conda activate'

Anytime you need conda command, you can first run conda_baseto get it.

Creating the Conda Environment

With Miniforge3 installed and the conda command available, you can create the Omega development environment, starting from the root of an Omega branch, with:

cd components/omega/
conda create -n omega_dev --file dev-conda.txt
conda activate omega_dev
pre-commit install

(You can reuse omega_dev for other branches as long as dev-conda.txt has not changed between branches.)

Updating the Conda Environment

If you need to update the omega_dev conda environment, the easiest way to do that is just to recreate it by following the same instructions as above. You will be prompted about whether you want to delete the old environment unless you include the -y flag (to say “yes” to all prompts).
